# Yazi keyboard behavior and browser focus

## What transfers from Yazi

- Yazi's shipped manager preset maps `j`/`k` to next/previous file, `h`/`l` to parent/child directory, and the corresponding arrow keys to the same actions. `Tab` invokes `spot` on the current item; `Tab` or `Esc` closes the spotter. See the `[mgr]` and `[spot]` layers in the [shipped keymap](https://github.com/sxyazi/yazi/blob/shipped/yazi-config/preset/keymap-default.toml) and the [official `spot` documentation](https://yazi-rs.github.io/docs/configuration/keymap/#mgr.spot).
- Upstream Yazi is keyboard-first, not keyboard-exclusive: its [shipped configuration](https://github.com/sxyazi/yazi/blob/shipped/yazi-config/preset/yazi-default.toml) enables `click`, `scroll`, and `drag` mouse events. The [configuration reference](https://yazi-rs.github.io/docs/configuration/yazi/#mgr.mouse_events) documents which events plugins can receive and how to disable mouse events. That capability does not require mouse gameplay here. [PRODUCT.md](../PRODUCT.md) sets the game’s scope: desktop play without a pointer; touch-only gameplay is outside scope.

## What the browser adds

- [WCAG 2.2 §2.1.1](https://www.w3.org/TR/WCAG22/#keyboard) requires keyboard operability, not mouse controls or one particular key for each action. [§2.1.2](https://www.w3.org/TR/WCAG22/#no-keyboard-trap) requires a keyboard way out; when it is not a standard exit method, tell users how to leave. W3C's [no-trap guidance](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) explicitly gives a puzzle that handles Tab as an example, provided it gives an exit instruction before and inside the puzzle.
- [§2.1.4](https://www.w3.org/TR/WCAG22/#character-key-shortcuts) allows printable shortcuts that are active only while their component has focus; turning them off or remapping them with a non-printable key are the other alternatives. W3C's [explanation](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html) includes printable sequences, not just individual keys. Keeping `j`, `k`, and `gg` inside the focused game pane is compatible with that criterion; handling them across the page is not the same as focus scoping.
- The [APG keyboard guide](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) recommends a predictable tab order between components, visible focus, and keeping focus separate from selection. Its [modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) recommends a named dialog, initial focus inside, Tab and Shift+Tab containment, Escape to dismiss, and return to the opener or logical successor. Those are design patterns, not a conformance verdict.

## Recommendation for Yazi Quest

Treat **Tab-to-inspect as a Yazi command inside the active file pane**, and **Tab as browser focus navigation outside gameplay**. `handleSystemParams.ts` currently prevents the default Tab action and updates file-info/scouting state; `App.tsx` routes game keys through a window-level registration, and the [desktop audit](accessibility-audit.md) observed Tab being consumed from the body. The binding is authentic; the scope is the browser-specific problem. Keep the existing Yazi command and its task predicates. Keep Map, Hint, and Help shortcuts as game controls, not upstream Yazi bindings.

The audit's body-Tab observation is a focus-discovery problem, not by itself proof of a keyboard trap or a failure of keyboard operability. The existing `Alt+M`, `Alt+H`, and `Alt+?` routes already open Map, Hint, and Help from the keyboard. The next check is whether players can enter, operate, and exit all relevant controls and states without a pointer.

First implementation to test: focus the active file pane when play begins, give it a visible focus treatment, and try ordinary `Shift+Tab` from the pane to the controls before adding a new shortcut. Preserve inspection's `Tab`/`Esc` dismissal and return focus to the pane; if inspection becomes modal, give it an operable Close action as well. The player must be able to leave inspection and reach the controls without clearing the **marked selection**. Return focus to the opener or logical successor after other dialogs and text entry. Native labelled fields own editing keystrokes; game commands should not run while typing or operating toolbar controls.

Acceptance examples: play starts without a click; `j` moves the current item without marking it; `Tab` still opens inspection and counts for the same objectives; a player can exit using only the keyboard, operate Help/settings, and return to the same game context; text entered into Search does not move the file cursor. Check these in Chromium and a desktop screen reader before claiming the focus design is accessible. This note does not change keybindings or establish WCAG conformance.
